# Design: `depends_on` execution DAG for Supervisor (3.3)

Status: **proposed** (design review before implementation)
Target release: 3.3.0
Covers roadmap items: #22 (dependency DAG), #9 (sequential vs parallel
rules), #7 (Specialist model), #23 (conditional execution). Hooks for
#24 (confidence routing) without implementing it.

---

## 1. Problem

The Supervisor today has two execution modes, and each has half of what
a real pipeline needs:

| Mode | Parallelism | Context threading |
|---|---|---|
| `Supervisor` / `AsyncSupervisor(sequential=True)` | none - strict plan order | full - every step receives ALL prior results (`_build_augmented_query`) |
| `AsyncSupervisor(sequential=False)` | full - every step at once | **none** - `_run_subtask` is called without `prior_results` (Supervisor.py, `astream`, concurrent branch) |

So a plan like this cannot execute correctly today:

```
intent ──> retrieve ──> rerank        (chain: needs threading)
summary_A                             (independent: could run parallel)
summary_B                             (independent: could run parallel)
```

Sequential mode runs `summary_A`/`summary_B` needlessly late and feeds
them irrelevant context (the whole intent/retrieve/rerank output is
prepended to their queries, wasting tokens and diluting attention).
Concurrent mode runs everything at once and the chain breaks: `rerank`
executes with no candidates.

A second, subtler problem: even in sequential mode, context routing is
"everything prior", not "what this step depends on". Step 5 of a
5-step plan receives four prior results whether it needs them or not,
and the per-entry context budget (`max_context_chars // len(useful)`)
shrinks as the plan grows - the one result a step actually needs gets
truncated to make room for three it doesn't.

Dependencies solve ordering, parallelism, AND routing with one
declaration.

---

## 2. Design overview

Two layers, one execution truth:

1. **Plan-level `depends_on` (execution truth).** The planner emits
   step `id`s and `depends_on` edges. The executor topologically sorts,
   runs independent steps concurrently (async) or in stable topo order
   (sync), and threads each step ONLY its direct dependencies' results.

2. **Registry-level `Specialist` metadata (planner hints).** An
   optional `Specialist` model replaces the bare
   `(description, runner)` tuple. Its `depends_on` field names other
   specialists as a *hint injected into the planning prompt* - not an
   execution constraint. Rationale: the same specialist can appear
   twice in one plan (researcher for topic A and topic B), so
   name-level dependencies are ambiguous at execution time; step-ids
   are not.

### New plan format

```json
{
  "plan": [
    {"id": "intent",    "agent": "intent",    "query": "..."},
    {"id": "retrieve",  "agent": "retriever", "query": "...", "depends_on": ["intent"]},
    {"id": "rerank",    "agent": "reranker",  "query": "...", "depends_on": ["retrieve"]},
    {"id": "summary_a", "agent": "researcher", "query": "Summarize topic A"},
    {"id": "summary_b", "agent": "researcher", "query": "Summarize topic B"}
  ]
}
```

Execution (async): wave 1 = `{intent, summary_a, summary_b}` run
concurrently; `retrieve` starts the moment `intent` lands (not when the
whole wave finishes - completion-driven, not barrier-driven); `rerank`
after `retrieve`. Sync runs the same graph in stable topological order.

### Backward compatibility (hard requirement)

- Steps missing `id` are auto-assigned `step_1`, `step_2`, ... in plan
  order.
- **If NO step in the plan carries `depends_on`, the run uses legacy
  semantics unchanged**: sequential mode threads all-prior results
  exactly as today; async concurrent mode runs everything independent
  exactly as today. Existing users see byte-identical behaviour.
- If ANY step carries `depends_on`, the plan is a DAG: steps without
  `depends_on` are roots (no implicit chain to prior steps).
- `SupervisorResult` / `SubtaskResult` shapes only gain optional
  fields; existing consumers unaffected.

## 3. Detailed design

### 3.1 Plan sanitization (never fail the run)

After `_plan()` parses the JSON, a pure function normalizes the graph:

```python
def _sanitize_plan(plan: List[dict], verbose: bool) -> List[dict]:
    """id assignment, dep validation, cycle breaking. Deterministic;
    never raises. Warns (verbose) on every repair it makes."""
```

Rules, in order:

1. **Auto-id.** Missing/duplicate `id` -> assign `step_N` (N = 1-based
   plan position). Duplicates keep the first occurrence; later ones are
   renamed `step_N` and a warning names the collision.
2. **Unknown deps dropped.** `depends_on` entries that name no step id
   are removed with a warning ("step 'rerank' depends on unknown
   'retreive' - dropped"). A typo degrades to a root step, not a dead
   run. (Planner typos are the common case; see also 3.6 replan.)
3. **Self-deps dropped.**
4. **Cycle breaking.** Kahn's algorithm; if a cycle remains, drop the
   edge that points from the LATEST plan position to the EARLIEST
   (the back-edge in plan order) and re-run. Deterministic, and plan
   order is the planner's own statement of intended sequence, so the
   forward reading survives.
5. **`__spawn__` steps** keep today's semantics: executed at their plan
   position before any dependent dispatch, never parallelized, cannot
   be depended on (a dep naming a spawn step's id is dropped with a
   warning).

Sanitization is exposed as a module-level function so it is unit-testable
without a model.

### 3.2 Execution: sync (`Supervisor.stream`)

Replace the linear `for item in plan` walk with stable topological
order (Kahn's; ties broken by plan position). For each step:

```python
dep_results = [results_by_id[d] for d in step["depends_on"] if d in results_by_id]
query = _build_augmented_query(step["query"], dep_results)   # unchanged fn
```

`_build_augmented_query` itself does not change - it already handles
structured outputs (3.2), truncation, and the no-priors passthrough.
What changes is WHAT gets passed: direct dependencies only, instead of
everything prior. In legacy mode (no deps anywhere) the call site passes
all prior results, exactly as today.

Direct deps only - not transitive. If `rerank` needs the original
`intent` output as well as `retrieve`'s, the planner writes
`depends_on: ["intent", "retrieve"]`. Explicit routing is the point;
silently forwarding transitive closures reintroduces the context bloat
this design removes. The planner prompt documents this.

### 3.3 Execution: async (`AsyncSupervisor.astream`)

Completion-driven scheduler replacing the current two branches:

```python
ready    = steps whose deps are all in results_by_id (initially: roots)
running  = {}   # task -> step
while ready or running:
    for step in ready: spawn _run_subtask(agent, query, dep_results)
    done, _ = await asyncio.wait(running, return_when=FIRST_COMPLETED)
    for t in done:
        record result; yield subtask_result event
        promote newly-ready dependents into `ready`
```

- `sequential=True` keeps meaning "no concurrency": the same scheduler
  with a max-parallelism of 1, in stable topo order. The flag's
  docstring changes from "thread results" to "limit parallelism" -
  threading is now dependency-driven in both modes.
- A new `max_parallel: Optional[int]` (default `None` = unbounded)
  caps concurrent sub-tasks for rate-limit-constrained deployments.
  `sequential=True` is sugar for `max_parallel=1`.

### 3.4 Failure and skip propagation

If a step still has `error` set after `_dispatch_with_retry` /
`subtask_success_check`, every step depending on it (transitively) is
**skipped**, not run:

```python
SubtaskResult(
    agent=..., query=...,
    content="",
    error="skipped: dependency 'retrieve' failed (<its error>)",
    skipped=True,
)
```

Skipped steps yield `subtask_result` events like any other, so UIs see
the full picture. Independent branches keep running - one failed chain
does not abort the plan. Synthesis runs over whatever succeeded (the
synthesize prompt already handles missing data honestly).

Rejected alternative: running dependents anyway with an error note.
That produces confident garbage downstream of garbage; skip is
deterministic and the retry machinery already exists at the step level.

### 3.5 Conditional execution (#23): `skip_when`

Minimal, deterministic, evaluated in Python - no LLM call:

```json
{"id": "retrieve", "agent": "retriever", "query": "...",
 "depends_on": ["intent"],
 "skip_when": {"step": "intent", "field": "needs_rag", "is": false}}
```

Semantics:

- Evaluated when the step becomes ready (deps done).
- `step` must be a direct dependency; `field` is looked up on that
  step's `SubtaskResult.output` (the 3.2 typed instance) via
  `getattr`, falling back to dict access. Dotted paths
  (`"field": "meta.confidence"`) supported by chained lookup.
- `is` compares with `==`. That is the whole operator set for 3.3 -
  no `gt`/`lt`/`in` until real usage demands them.
- **Fail-open:** if the dep has no `output`, the field is missing, or
  anything raises -> the step RUNS. A skip must be provably justified.
- A skipped-by-condition step gets
  `error=None, skipped=True, content="skipped: intent.needs_rag == False"`,
  and its dependents treat it as an EMPTY success (they run, with no
  context contribution from it) - unlike failure-skips, which cascade.
  Rationale: `needs_rag=False` means "retrieval unnecessary", not
  "answering impossible"; the answer step should still run.

This gives #23's "skip retrieval for greetings" case. Confidence
routing (#24) is NOT implemented, but `skip_when` on a
`confidence`-typed field already covers its simplest form, and the
planner hint text (3.7) leaves room to document thresholds later.

### 3.6 Planner prompt changes

`SUPERVISOR_PLAN_PROMPT` gains the `id`/`depends_on`/`skip_when` format
and three rules:

- Add `depends_on` ONLY when the step consumes the earlier step's
  output. Independent steps must NOT be chained - missing edges are
  what unlocks parallelism.
- Dependencies are direct: list every step whose output this step
  reads, not just the latest.
- `skip_when` only against a typed field of a direct dependency
  (the agent catalog now shows each specialist's output schema name +
  fields when declared - see 3.7).

Plan-repair loop: if sanitization made ANY repair (dropped dep, broken
cycle), and `max_plan_retries >= 1` (new knob, default 1), the plan is
re-requested once with the repair warnings appended to the prompt -
same philosophy as `_augment_query_with_error`. The sanitized plan is
kept as fallback if the retry is no better.

### 3.7 `Specialist` model (#7)

```python
@dataclass
class Specialist:
    description: str
    runner: Any                      # AgentRunner | AsyncAgentRunner
    depends_on: List[str] = field(default_factory=list)   # planner hint
    output_schema: Optional[type] = None   # informational; catalog display
    when_to_use: str = ""                  # extra planner guidance
```

- `agents={}` accepts `Specialist` OR the existing
  `(description, runner)` tuple; tuples are wrapped internally
  (`Specialist(description=d, runner=r)`). No deprecation.
- `output_schema` defaults from `runner.output_schema` when unset, so
  3.2 users get catalog display for free.
- `_build_agent_catalog` renders the extras:

```
- retriever: Retrieves candidates as structured JSON.
    typically after: intent
    returns: RetrievalBatch(ids, texts, vector_scores, metadata)
    use when: the knowledge base must be consulted
```

The `typically after:` line is exactly that - a hint. The planner may
ignore it (e.g. a task that needs retrieval without intent analysis).
Execution never reads `Specialist.depends_on`.

### 3.8 Result-shape additions (all optional)

```python
class SubtaskResult(BaseModel):
    ...existing...
    step_id: Optional[str] = None
    depends_on: List[str] = Field(default_factory=list)
    skipped: bool = False
```

`SupervisorResult.plan` already stores raw dicts, so `id`/`depends_on`
flow through untouched. Stream events gain `"step_id"` alongside the
existing positional `"step"` index.

## 4. What this deliberately does NOT do

- **No nested DAGs / sub-plans.** One level, as today. Hierarchy =
  a supervisor inside a specialist.
- **No dynamic graph edits mid-run** (except the existing `__spawn__`
  path). Replanning-on-failure is a 3.4+ conversation.
- **No transitive context forwarding** (see 3.2 rationale).
- **No rich `skip_when` operators** until usage shows which are needed.
- **No confidence-routing engine** (#24) - only the `skip_when` seam.

## 5. Test plan

Pure-function tests (no model):
- `_sanitize_plan`: auto-id, duplicate ids, unknown dep, self-dep,
  2-cycle, 3-cycle, spawn-step deps, no-deps legacy detection.
- Topo order stability: same plan -> same order, ties by position.
- `skip_when` evaluation: typed output, dict output, missing field
  (fail-open), dotted path, non-dep step reference (fail-open + warn).

Stub-model integration tests (pattern used throughout 3.2 testing):
- Chain + independent mix: assert `rerank` saw ONLY `retrieve`'s
  result in its query; assert `summary_a` saw no prior context.
- Async: assert `intent`, `summary_a`, `summary_b` overlap in time
  (start-order instrumentation on the stub) while `rerank` starts
  after `retrieve` completes.
- Failure cascade: fail `retrieve`, assert `rerank` skipped with
  cascade error, `summary_*` unaffected, synthesis ran.
- Condition skip: `needs_rag=False` -> `retrieve` skipped,
  answer step still ran.
- Legacy: dep-free plan produces byte-identical augmented queries to
  3.2 (regression capture).

## 7. Implementation order

1. `_sanitize_plan` + tests (pure, no risk).
2. `Specialist` + catalog rendering (additive, no execution change).
3. Sync topo execution + direct-dep threading + legacy detection.
4. Async completion-driven scheduler + `max_parallel`.
5. Failure/skip propagation + `skip_when`.
6. Planner prompt + plan-repair loop.
7. Docs + cookbook + CHANGELOG + release.

Steps 1-2 are shippable alone; 3-5 are the core and land together;
6 last because prompt changes are cheapest to iterate once execution
is observable.
